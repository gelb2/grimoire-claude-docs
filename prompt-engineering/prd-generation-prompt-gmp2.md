# 범용 PRD 즉시 생성 프롬프트 (GMP v2.0 적용)

> **사용법**: 기획 대화가 충분히 진행된 시점에, 아래 코드블록 안의 프롬프트를 그대로 붙여넣으면
> 대화 컨텍스트를 자동 참조하여 개발 착수 가능 수준의 PRD를 `.md` 파일로 생성합니다.

---

````
지금까지 대화에서 논의한 내용을 모두 참조하여, 아래 지시사항에 따라 PRD를 마크다운(.md) 파일로 작성하라.

<CRITICAL_CONSTRAINTS>
[MUST] 대화에서 논의된 모든 기능, 비즈니스 로직, 도메인 규칙, 기술 제약을 빠짐없이 반영하라.
[MUST] 모든 핵심 로직(계산식, 비즈니스 룰, 상태 전이 등)은 수식/규칙 + 실제 예시 2세트를 병기하여 검증 가능하게 작성하라.
[MUST] 각 기능은 반드시 [Why(사용자 시나리오) → 입력값 → 출력값 → 처리 로직 → UI 동작] 순서로 기술하라.
[MUST] 해당 도메인의 법적·제도적·관행적 특수성을 정확히 반영하라. 대화에서 확인되지 않은 사항은 [미확인] 태그를 부착하고, 사용자 설정 가능하게 설계하라.
[MUST] 외부 의존성이 있는 변수는 수동 입력 폴백을 함께 설계하라.
[MUST] MVP(v1)는 최소 외부 의존성으로 독립 동작 가능하게 설계하라.
[MUST] 한국어 마크다운 파일로 출력하라. 데이터 모델은 테이블, 화면 흐름은 Mermaid 다이어그램을 사용하라.
[MUST] 대화에서 직접 확인되지 않은 정보를 기반으로 작성한 부분에는 [추론] 태그를 부착하라.
</CRITICAL_CONSTRAINTS>

<ROLE>
해당 프로젝트 도메인에 정통한 시니어 PM. 타겟 사용자의 핵심 워크플로우를 깊이 이해하며, 비즈니스 로직의 정확성과 개발 구현 가능성을 동시에 고려하여 PRD를 설계한다.
</ROLE>

<CONTEXT>
<CONTEXT_EXTRACTION>
PRD 작성 전에, 지금까지 대화에서 다음 8개 항목을 추출·정리하라. 대화에서 명시적으로 논의되지 않은 항목은 프로젝트 맥락에서 추론하되, [추론] 태그를 부착하라.

1. **제품 정의**: 무엇을 만드는가, 핵심 가치 제안
2. **타겟 사용자**: 누구를 위한 것인가, 페르소나
3. **도메인 규칙**: 반드시 지켜야 할 제도/규칙/법적 요건
4. **핵심 비즈니스 로직**: 계산 공식, 상태 전이, 분기 규칙
5. **사용자 페인포인트**: 기존 대안의 한계, 해결할 문제
6. **기능 범위**: 논의된 기능 목록과 우선순위 감각
7. **기술 제약**: 스택, 아키텍처, 배포 환경 합의 사항
8. **시장 파라미터**: 도메인 기본값, 범위, 외부 변수
</CONTEXT_EXTRACTION>
</CONTEXT>

<AGENT_ARCHITECTURE>
<ORCHESTRATOR>
**PRD 총괄 에이전트**
- 대화 컨텍스트에서 추출한 정보 기반 전체 PRD 구조 설계
- 서브에이전트 산출물을 통합하여 최종 PRD 조립
- 핵심 로직 교차 검증 (도메인-검증자 결과 vs 기능-설계자 적용 결과 대조)
- 대화에서 논의되었으나 PRD에 누락된 항목 최종 점검
</ORCHESTRATOR>

<SUB_AGENT name="도메인-검증자" scope="도메인 제도 정확성 및 비즈니스 로직 검증">
**입력**: CONTEXT_EXTRACTION에서 추출한 도메인 규칙 + 비즈니스 로직
**작업**:
1. 핵심 비즈니스 로직을 실제 숫자/시나리오 2세트로 대입 검증
   - 세트A: 대표적 일반 케이스
   - 세트B: 극단적이지만 현실적인 케이스
2. 도메인 규칙의 경계값(boundary) 케이스 검증
3. 외부 의존 변수 → "사용자 설정 변수" 테이블 정리
4. 엣지 케이스 최소 5개 도출 (비정상 입력, 제도적 예외, 타이밍 이슈, 데이터 누락, 동시성)
**출력**: 검증된 로직 목록 + 엣지 케이스 목록 + 숫자 예시 2세트 + 사용자 설정 변수 테이블
**완료 기준**: 모든 핵심 로직이 2개 시나리오에서 교차 검증 완료
</SUB_AGENT>

<SUB_AGENT name="기능-설계자" scope="기능별 상세 명세 작성">
**입력**: CONTEXT_EXTRACTION의 기능 범위 + 도메인-검증자의 검증된 로직/엣지 케이스
**작업**:
1. 대화에서 논의된 기능을 Tier 1~4로 분류 (미분류 시 맥락 기반 추론 + [추론] 태그)
2. Tier 1(코어) + Tier 2(확장) 기능을 명세 템플릿으로 상세 작성
3. Tier 3~4는 기능명 + 한줄 설명 + 우선순위만 기술
4. MoSCoW 기준 우선순위 분류표 작성
5. 기능 간 의존 관계 Mermaid 다이어그램 작성
**출력**: 기능 명세서 (기능당 1 섹션) + MoSCoW 표 + 의존 관계 다이어그램
**완료 기준**: Tier 1 전체 + Tier 2 전체 상세 명세 완료
</SUB_AGENT>

<SUB_AGENT name="기술-설계자" scope="IA, 데이터 모델, 기술 스택, UI 구조">
**입력**: 기능-설계자의 기능 명세서 + CONTEXT_EXTRACTION의 기술 제약
**작업**:
1. 정보 아키텍처 (탭/섹션 구조, 화면 흐름)
2. 데이터 모델 (엔티티, 필드, 타입, 관계 — 마크다운 테이블)
3. 기술 스택 상세 (대화에서 합의된 스택 우선, 없으면 추천 + 선택 근거)
4. MVP vs Full 아키텍처 분리
5. 화면 흐름 Mermaid 다이어그램
6. KPI 정량 목표 + 로드맵 (v1 → v2 → v3)
**출력**: IA 문서 + 데이터 모델 + 기술 스택 + Mermaid + KPI + 로드맵
**완료 기준**: 개발자가 바로 구현에 착수할 수 있는 수준의 구체성
</SUB_AGENT>

<HANDOFF_PROTOCOL>
1. CONTEXT_EXTRACTION 완료 → 도메인-검증자에 전달
2. 도메인-검증자 완료 → [HANDOFF] 블록으로 검증된 로직 + 엣지 케이스 → 기능-설계자에 전달
3. 기능-설계자 완료 → [HANDOFF] 블록으로 기능 명세서 → 기술-설계자에 전달
4. 기술-설계자 완료 → Orchestrator가 전체 통합 → 교차 검증 → 최종 PRD 출력
각 단계의 [HANDOFF] 블록에는 다음 에이전트가 참조할 핵심 데이터를 명시하라.
</HANDOFF_PROTOCOL>
</AGENT_ARCHITECTURE>

<STEP n="0" label="상위 원칙 도출 (Step-Back Abstraction)">

5. **일관성**: PRD 전체에서 동일 개념에 동일 용어가 사용되었는지 확인하라.
6. **[추론] 태그 점검**: 대화에서 확인되지 않은 정보 기반 작성 부분에 빠짐없이 태깅되었는지 확인하라.
7. **대화 누락 점검**: 대화에서 합의되었으나 PRD에서 빠진 항목이 없는지 최종 확인하라.
</SELF_VERIFICATION>

<FINAL_REMINDER>
■ 최종 확인 — 핵심 제약을 재확인하라:
- [MUST] 대화에서 논의된 모든 기능·로직·제약을 빠짐없이 반영

- [MUST] 도메인 특수성 정확 반영 + 미확인 사항은 [미확인] 태그
- [MUST] 가변 파라미터는 사용자 설정 가능하게 설계
- [MUST] MVP는 최소 외부 의존성으로 독립 동작
- [MUST] 한국어 마크다운 파일 출력, 데이터 모델은 테이블, 화면 흐름은 Mermaid
- [MUST] 추론 기반 작성 부분에 [추론] 태그 부착

출력물은 **개발자가 바로 구현에 착수할 수 있는 수준**의 구체성을 갖춘 PRD여야 한다.
지금 바로 PRD를 .md 파일로 작성하라.
</FINAL_REMINDER>
````

## 메타 정보

**적용 기법**:
- XML 태그 기반 계층 구조 + 이중 앵커링 (CRITICAL_CONSTRAINTS ↔ FINAL_REMINDER)
- Step-Back Abstraction (STEP 0 상위 원칙 도출)
- Chain-of-Verification (SELF_VERIFICATION 7단계)
- 우선순위 라벨링 ([MUST] / [SHOULD] / [NICE])
- 긍정형 지시 원칙 전면 적용

**서브에이전트 구성**:
Orchestrator → 도메인-검증자 → 기능-설계자 → 기술-설계자 (순차 핸드오프, Fresh Eyes 원칙)

**예상 실행 흐름**:
CONTEXT_EXTRACTION(대화 정보 추출) → STEP 0(상위 원칙) → STEP 1(도메인 검증) → STEP 2(기능 명세) → STEP 3(기술 설계) → STEP 4(통합) → SELF_VERIFICATION(7단계 검증) → .md 파일 출력

**사용 시 주의점**:
- 대화 컨텍스트가 충분히 축적된 시점(기능 범위·도메인 규칙·기술 스택 중 2개 이상 논의 완료)에서 사용할 것
- 출력된 PRD에서 [추론] 태그 항목은 반드시 검토 후 확정할 것

**선택적 강화**:
- 특정 기술 스택이 확정된 경우, CONTEXT 섹션에 `<TECH_STACK>` 블록을 추가하면 기술-설계자의 정확도 향상
- 경쟁사 분석이 필요한 경우 `<COMPETITIVE_ANALYSIS>` 서브에이전트 추가 가능
