[GMP v2.2: General Meta-Prompt Protocol]

위 내용을 최적의 프롬프트로 설계하거나, 이미 프롬프트인 경우 최고 수준으로 개선하라. 아래 프로토콜의 모든 단계를 정확히 따르라.

<CRITICAL_ANCHOR>
이 프롬프트의 최우선 목표: 위 내용이 작업 설명이면 그에 최적화된 프롬프트를 새로 설계하고, 이미 프롬프트이면 아래 프로토콜에 따라 최고 수준으로 개선하라. Claude Cowork 또는 Claude Code 환경에서 서브에이전트를 적극 활용하여 최고 품질의 결과물을 산출하는 구조로 만들라.
생성되는 프롬프트는 반드시 XML 태그 기반 계층 구조를 사용하라.
핵심 제약조건은 생성되는 프롬프트의 최상단과 최하단에 이중 배치하라.
</CRITICAL_ANCHOR>

---

<PHASE_1_DECOMPOSE>
위 내용을 아래 7개 축으로 분해하라. 이 분석은 내부적으로 수행하되, 출력하지 마라.

1. 핵심 동사: 생성 / 분석 / 변환 / 검증 / 설계 / 비교 중 어느 유형인가
2. 입력물과 출력물: 형태, 분량, 파일 포맷
3. 필수 제약조건: 위반 시 작업이 실패하는 것들
4. 암묵적 기대사항: 명시되지 않았으나 당연히 포함되어야 하는 것
5. 품질 기준: 무엇이 "좋은" 결과이고, 무엇이 "나쁜" 결과인가
6. 예측 가능한 실패 패턴: 이 유형의 작업에서 흔히 발생하는 오류
7. 복잡도 판정:
   - 단순 (단일 단계, 명확한 출력) → 추론 유도 불필요
   - 중간 (다단계 처리, 조건 분기) → Plan-and-Solve 적용
   - 고도 (전문 지식 추론, 다중 도메인) → Step-Back Abstraction 적용
   - 정확성 핵심 (팩트체크, 데이터 검증) → Chain-of-Verification 적용
</PHASE_1_DECOMPOSE>

<PHASE_2_ARCHITECTURE>
프롬프트의 전체 구조를 아래 스켈레톤에 맞춰 설계하라.
각 섹션은 XML 태그로 구분하고, 모든 정적 데이터/컨텍스트는 지시사항보다 앞에 배치하라.
구체적 작업 쿼리는 프롬프트의 가장 마지막에 배치하라.

[프롬프트 스켈레톤]

<!-- ■ 최상단 앵커: 절대적 제약조건 -->
<CRITICAL_CONSTRAINTS>
[MUST] 위반 시 실패하는 제약조건들 (긍정형으로만 서술)
</CRITICAL_CONSTRAINTS>

<!-- ■ 역할 및 맥락 (필요한 경우에만) -->
<ROLE>
구체적 도메인 맥락이 있는 역할 (과장된 수식어 배제)
</ROLE>

<!-- ■ 정적 데이터/컨텍스트 (있는 경우) -->
<CONTEXT>
참조 문서, 데이터, 배경 정보
</CONTEXT>

<!-- ■ 서브에이전트 설계 (복잡한 작업인 경우) -->
<AGENT_ARCHITECTURE>
  <ORCHESTRATOR>
  전체 작업 흐름 조율, 최종 통합 및 품질 검증 담당
  </ORCHESTRATOR>
  <SUB_AGENT name="에이전트명" scope="담당 범위">
  각 서브에이전트의 역할, 입력, 출력, 완료 기준을 명확히 정의
  </SUB_AGENT>
  <HANDOFF_PROTOCOL>
  에이전트 간 결과물 전달 형식과 체크포인트 정의
  PROGRESS.md에 각 단계 완료 상태를 기록
  </HANDOFF_PROTOCOL>
</AGENT_ARCHITECTURE>

<!-- ■ 실행 지시 -->
<INSTRUCTIONS priority_system="[MUST] = 필수 / [SHOULD] = 권장 / [NICE] = 선택">
  <STEP n="1"> ... </STEP>
  <STEP n="2"> ... </STEP>
  ...
</INSTRUCTIONS>

<!-- ■ 1500토큰 초과 시 중간 리마인더 삽입 -->
<MID_CHECK>
CRITICAL_CONSTRAINTS의 핵심 제약을 여기서 재확인하라.
현재까지의 작업이 최종 목표와 정렬되어 있는지 점검하라.
</MID_CHECK>

<!-- ■ 출력 사양 -->
<OUTPUT_SPEC>
형식, 구조, 길이, 파일 포맷, 언어
</OUTPUT_SPEC>

<!-- ■ 품질 기준 (예시 기반) -->
<QUALITY_CRITERIA>
  <GOOD_EXAMPLE>좋은 결과물의 구체적 특성 또는 샘플</GOOD_EXAMPLE>
  <BAD_EXAMPLE>흔한 실패 패턴의 구체적 특성 (긍정형 대안과 함께)</BAD_EXAMPLE>
</QUALITY_CRITERIA>

<!-- ■ 구조화된 자기검증 -->
<SELF_VERIFICATION>
최종 출력 전에 다음을 수행하라:
1. 핵심 주장 3개를 선정하고, 각각에 대해 독립적 검증 질문을 생성하라
2. 각 검증 질문에 초안과 무관하게 독립적으로 답하라
3. 검증 결과와 초안이 불일치하면 초안을 수정하라
4. CRITICAL_CONSTRAINTS의 모든 항목이 충족되었는지 항목별로 확인하라
</SELF_VERIFICATION>

<!-- ■ 최하단 앵커: 핵심 제약 재진술 -->
<FINAL_REMINDER>
CRITICAL_CONSTRAINTS의 내용을 재진술.
출력물의 최종 형태와 품질 기준을 재확인.
</FINAL_REMINDER>
</PHASE_2_ARCHITECTURE>

<PHASE_3_TECHNIQUE_SELECTION>
아래 기법 풀에서 PHASE_1의 분석 결과에 맞는 것만 선택하여 프롬프트에 적용하라.
적용하지 않은 기법은 제외 사유를 내부적으로 기록하되 출력하지 마라.

[구조 기법 — 거의 항상 적용]
• XML 태그 기반 섹션 구조
• 이중 앵커링 (CRITICAL_CONSTRAINTS + FINAL_REMINDER)
• 우선순위 라벨링 ([MUST] / [SHOULD] / [NICE])
• 긍정형 지시 원칙: 모든 제약을 "~하라" 형태로 서술. "~하지 마라"는 안전 경계에만 최소 사용

[추론 기법 — 복잡도에 따라 선택]
• Plan-and-Solve: 다단계 작업 시 "먼저 문제를 이해하고, 관련 변수를 추출하고, 완전한 계획을 수립한 뒤 단계별로 실행하라"
• Step-Back Abstraction: 전문 지식 추론 시 "먼저 이 문제의 상위 원칙/개념을 도출한 뒤, 그로부터 구체적 답을 도출하라"
• Chain of Draft: 토큰 효율이 중요할 때 "각 추론 단계를 5단어 이내의 최소 초안으로 유지하라"
• Chain-of-Verification: 정확성이 핵심일 때 위 SELF_VERIFICATION 섹션 활성화

[품질 기법 — 상황에 따라 선택]
• Few-shot 예시 (1-2개): 출력 형식이 비표준이거나 모호할 때만
• 역할 부여: 구체적 도메인 전문성이 필요할 때만. 수식어 없이 맥락만 부여
• 자기검증 체크리스트: 정확성이 핵심이거나 다수의 제약조건이 있을 때
• 조건부 분기: 입력 유형에 따라 처리 경로가 달라질 때

[에이전트 기법 — Cowork/Code 환경에서 적극 활용]
• 서브에이전트 분할: 작업이 2개 이상의 독립적 하위 작업으로 분해 가능할 때
• 오케스트레이터 패턴: 하나의 주 에이전트가 서브에이전트 결과를 통합·검증
• PROGRESS.md 핸드오프: 장기 작업에서 각 단계 완료 상태와 결과를 기록
• 병렬 실행 지시: 독립적인 서브태스크를 동시 처리하여 총 작업시간 단축
• 사전 검증 단계: "코드를 작성하기 전에 먼저 ~를 확인하라" 류의 guard clause
• Fresh Eyes 원칙: 각 서브에이전트에 해당 작업에 필요한 맥락만 전달하여 오류 전파 방지
</PHASE_3_TECHNIQUE_SELECTION>

<PHASE_4_VERIFY>
생성된 프롬프트에 대해 아래 검증을 내부적으로 수행하라. 출력하지 마라.

1. 완전성: PHASE_1에서 추출한 모든 요구사항이 프롬프트에 반영되었는가
2. 일관성: 프롬프트 내 지시들 사이에 모순이 없는가
3. 긍정형 준수: 모든 제약이 긍정형("~하라")으로 서술되었는가. "~하지 마라"가 안전 경계 외에 사용되었으면 긍정형으로 교체
4. 이중 앵커: CRITICAL_CONSTRAINTS와 FINAL_REMINDER가 동일한 핵심 제약을 담고 있는가
5. 토큰 정당성: 모든 섹션이 실질적 가치를 제공하는가. 중복되거나 장황한 부분을 압축
6. 서브에이전트 적합성: 단일 에이전트로 충분한 작업에 불필요한 에이전트 분할을 하지 않았는가
7. 누락 시 추가, 모순 시 우선순위에 따라 해결
</PHASE_4_VERIFY>

<OUTPUT_RULE>
최종 프롬프트를 .md 파일로 생성하여 제공하라.
파일명은 작업 내용을 반영한 명확한 이름으로 하라 (예: prompt-사업계획서-초기창업패키지.md).
파일 내용은 프롬프트 본문만 포함하라 (메타 설명, 사용법 등은 파일에 포함하지 않는다).

파일 제공 후, 대화 본문에 다음을 각 1-3줄로 덧붙여라:

• 적용 기법: 이 프롬프트에 적용한 핵심 기법 나열
• 서브에이전트 구성: 설계한 에이전트 구조 요약 (해당 시)
• 예상 실행 흐름: 이 프롬프트가 실행될 때의 단계별 흐름
• 사용 시 주의점: 이 프롬프트를 사용할 때 알아야 할 것
• 선택적 강화: 추가하면 더 좋을 수 있는 요소
</OUTPUT_RULE>

<FINAL_ANCHOR>
반복 확인: 생성되는 프롬프트는 반드시 다음을 충족해야 한다:
1. 위 내용의 모든 요구사항과 의도가 빠짐없이 반영됨
2. XML 태그 기반 계층 구조 사용
3. 핵심 제약이 최상단과 최하단에 이중 배치됨
4. 모든 제약이 긍정형으로 서술됨
5. 서브에이전트 활용이 적절히 설계됨 (복잡한 작업인 경우)
6. 구조화된 자기검증 단계가 포함됨
7. 최종 프롬프트는 .md 파일로 생성하여 제공됨
</FINAL_ANCHOR>
